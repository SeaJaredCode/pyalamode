# Acceptance and verification matrix

Source of truth: [SPEC-sol6.1-composite.md](../../SPEC-sol6.1-composite.md), read in full on 2026-10-09. This is a verification inventory for the proposed contract, not a record that the implementation or release gates have passed. Every expansion inherits earlier acceptance scenarios. A passing audit, a runtime marker, or a declaration alone supplies no strict evidence.

Evidence classes:

- **H — hard acceptance:** observable contract behavior, rejection, or required published claim. An unsupported case must remain unverified; passing narrower fixtures cannot establish broader admission.
- **E — engineering evidence:** operation/runtime contracts, explicit assumptions, adversarial results, compatibility records, and measured costs needed to justify a release or expansion.
- **U — user measurement:** observations from actual target users. Developer assertions, automated tests, and an agent completing the workflow do not establish these targets.
- **X — separately gated extension:** milestones 12–14. They retain H/E/U requirements and cannot become prerequisites for the useful core in milestones 1–11.

All checks below use public commands, ordinary Python execution, published contracts/reports, and observable library behavior. They do not prescribe checker, storage, compiler, or editor architecture. Fixture syntax for later capabilities must follow the admitted syntax published for that milestone.

## Cross-milestone dependencies and gate reconciliation

The only earlier acceptance row that demands a capability explicitly delivered later is **A24**. The agreed reconciliation preserves its whole scope: compatible-source/editor and guard diagnostics are milestone 9 requirements; translated-source diagnostics and authored-boundary mapping are verified at milestone 14. Milestone 9 does not wait for optional syntax, and milestone 14 cannot waive the translated portion.

No other unavoidable circular release gate was found. Ordinary prerequisites follow the roadmap: stable callable/capture contracts (2) support collection callbacks (3); collections (3) support nested records/conversions (4); effects (5) support effect-aware handlers (6), standard effect operations (7), integration review (8) and task effects (13); editor/policy/distribution inherit their earlier evidence. These are dependencies, not reasons to make a later extension a core prerequisite.

Two apparent later dependencies do not require a gate change: A13 can reject effectful/unknown callbacks at 3 without implementing checked effectful-shell execution at 5; A22 can identify installed ordinary dependencies at 8 without waiting for checked-package distribution at 11. Likewise initial checked builds at 1 need not provide the consumer-distribution evidence introduced at 11. Freshness applies from the first evidence/cache introduced at 1 (§5.2); 2/A10 adds application dependency graphs and 11/A28 adds consumer artifact verification.

## Engineering decisions and unobserved measurement gates

These decisions and evidence requirements must be resolved before their gates pass. They do not block starting a closed increment: builders may choose a finite supported syntax/operation set and publish its contract before admitting it. They are not additional milestone dependencies or proposed architecture:

- **Runtime scope (1):** publish the supported CPython 3.13 patch range and execute the declared macOS/Linux compatibility matrix. A singleton 3.13.1 range is sufficient when both platform results exist; broader patches are required only if the release claims them.
- **Admitted expansions (2–8, 12–14):** publish exact callable/annotation/pattern/failure syntax and operation/runtime contracts before admitting those features; unknown syntax or behavior remains unsupported meanwhile.
- **Collections and guards (3–4):** select and disclose backend/license/trust/complexity/retention evidence, plus guard export selection, validation coverage and measured overhead. Constructors and boundary guards require separate claims.
- **Integration sample (7–8):** select at least two bounded external integrations, their supported installed identities/versions, and representative target-user tasks. “Two integrations” is a required gate, not evidence supplied by naming arbitrary libraries.
- **Usability (1, 9, 14):** define representative tasks, participant criteria, measurement protocol and the pass decision before claiming roughly fifteen-minute onboarding, new-Python-user repair or sufficient dialect benefit. Only onboarding has a rough time target; the spec supplies no numerical editor-repair or dialect-benefit threshold.
- **Performance (beginning in the core):** name workloads, hardware, cold/warm conditions and dependency fanout, and publish observed runtime/memory costs. The spec requires measured evidence but defines no universal latency, throughput or memory threshold.

Do not delete or mark these gates passed because the current host cannot supply their evidence. Core implementation and local conformance can progress while platform and U claims remain explicitly unverified; each release or extension still needs its full gate.
